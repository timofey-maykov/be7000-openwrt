# 补丁

[Русский](patches.md) · [English](patches.en.md)

这里列出在 OpenWrt main（提交 d958caf）和 kravasuper 移植版之上加的所有改动。移植版本身以补丁系列的形式放在 [patches/port](../patches/port)。内核补丁在 [patches](../patches)，构建时复制到 target/linux/qualcommbe/patches-6.18。对 OpenWrt 源码树本身的改动在 [patches/tree](../patches/tree)。

## 为什么需要最早的几个补丁

移植版的镜像在我的板子上起不来。指示灯快速闪白光，没有网络，也没有 Wi-Fi，断电重启七次以后引导程序就切回原厂固件。在移植版的讨论帖里，遇到这个问题的不止我一个，大家一般把它归到主板版本不同上。板子上的 UART 是 1.8 V 的，我手上没有对应的转接器，所以只能从固件自己写进闪存的日志里找原因。具体怎么做的见 [debugging.zh.md](debugging.zh.md)。

最后查出来，启动失败是三个互相牵连的 bug 造成的。

1. **QCA8084 PHY 驱动**在配置完成后马上等 100 ms 的 BaseR 链路，等不到就返回错误。可是这条链路依赖 SoC 发出的信号，而 SoC 要等端口打开以后才开始发。如果引导程序已经把 SerDes 配好了，检查就能通过。我的板子上没有配好，日志里有 `BaseR link failed!` 和 `PPE port 1 failed to connect phylink`。补丁 0901 把这个错误改成了警告。
2. **qcom-ppe** 遇到这个错误后会把自己拆掉，并对一个已经关掉的 NAPI 再调用一次 `napi_disable()`。这样的调用永远不会返回。`insmod` 卡住，而模块是由 `S10boot` 加载的，所以后面的东西全都起不来。没有网络，没有 SSH，也没有 Wi-Fi。对应补丁 0900。
3. **还是这一段代码，在清理端口的地方**，去掉卡死以后，索引 `i` 会变成负数，代码去读数组开头之前的内存，结果就是 oops。对应补丁 0902。

后两个补丁修的是驱动里真实存在的 bug，和具体板子无关，值得提交到上游。第一个只是绕过问题，正确的做法是在挂接 PHY 之前先把 SoC 这边的 SerDes 配好。

## 内核补丁

| 补丁 | 作用 |
|------|-----------|
| 0900 | qcom-ppe，拆除收发环时不再第二次关闭 NAPI，否则 insmod 会持有 RTNL 永远卡住 |
| 0901 | QCA8084，挂接 PHY 时没有 BaseR 不再算错误，只给出警告 |
| 0902 | qcom-ppe，回滚端口设置时索引不会变成负数 |
| 0903 | QCA8084，如果挂接时 BaseR 没有锁定，在第一次 link up 时重新配置 XPCS |
| 0904 | qcom-ppe，EDMA 接收缓冲区映射和解除映射用同一个 DMA 方向（来自 OpenWrt main，0362） |
| 0905 | qcom-ppe，EDMA 接收每一轮都取下一个缓冲区。以前丢掉一帧以后，循环会拿到一个已经释放的缓冲区 |
| 0906 | qcom-ppe，多字宽的 PPE 表按整行写入，只写一个字的话硬件会丢掉这次写入 |
| 0907 | qcom-ppe，PPE 里的端口桥接由模块参数 bridge_offload 打开，默认关闭 |
| 0908 | spi-qpic-snand：如果 8 位 ECC 放不进页面及其 OOB，则改用 4 位。用于配备 ESMT F50D1G41LB 闪存（OOB 64 字节）的较新 BE7000 主板，原厂固件在这种闪存上使用 ECC4，8 位无法容纳 |

## OpenWrt 源码树的改动

| 补丁 | 作用 |
|------|-----------|
| 001 | BE7000 DTS，像原厂固件一样切换 5 GHz 射频通路（TLMM6 和 TLMM7），不切的话 5 GHz 接收很弱。另外加了 mtdoops 和设置卷用的内核参数 |
| 002 | 设备配置，kmod-ath11k-ahb，没有它内置的 2.4 GHz 射频就没有驱动 |
| 003 | sysupgrade 写入当前启动所在的槽位 |
| 004 | 内核配置里打开 mtdoops |
| 006 | BE7000 DTS，为 5 GHz dual-MAC 固件的 MLO 全局内存预留 12 MB，和原厂固件的 mlo_global_mem 一样 |
| 014 | PPE 硬件加速，来自 OpenWrt PR 24178 的补丁系列，见下文 |
| 005 | BE7000 DTS，内核不再通过 RPM 给 l2 稳压器投票，和原厂固件一样。有了这个请求，部分板子上 QCA8084 过来的 UNIPHY0 通道收不到数据，也就是以太网完全不通。USB 改用固定的 1.8 V 供电 |
| 015 | ath11k-firmware，不再检查由 git 打包出的压缩包的哈希。这个哈希取决于构建机器上的 git、tar 和 zstd，CI 运行器镜像更新后同一个提交打出了不同的哈希，构建因此在 "Hash mismatch" 处中断。源码提交本身仍然是固定的 |

## 硬件加速（PPE）

PPE 网络引擎自己就能做路由和 NAT，但 OpenWrt 里它的驱动目前只会把包交给 CPU。加速功能基于 OpenWrt 还没合并的 PR 24178，也就是 tree 014 里的 0500-0520 系列，去掉了其中的文档部分。它包括 switchdev 桥接、L3 流表、netfilter flowtable 加速、IPv6、PPPoE、WAN 上的 VLAN 以及给 Wi-Fi 用的虚拟端口。在 BE7000 上直接用是不行的，需要加上我们自己的修复。

- 0906。PPE 只有在多字宽表的一整行都写完以后才会生效。原来的补丁系列只改单个字，结果端口没有 L3 接口，PPPoE 也没有 router MAC 位。流表项装上了，但从来没有命中过，所有流量都以 L3 no-route 的原因送到 CPU。
- mac80211 393（patches/mac80211-subsys）。ath12k 没有实现 net_fill_forward_path，mac80211 于是返回错误，内核就把经过网桥到 Wi-Fi 客户端的整条路径丢掉了。流表项的输出设备一直是 br-lan，PPE 拒绝了所有回程方向。现在对于接入点，路径会一直走到 Wi-Fi 接口本身。
- 0905。驱动自己接收路径里的 bug，不开加速也存在。
- 0907。以前端口一加入网桥，PPE 桥接就启动了。现在这是一个单独的选项。

实际效果是这样的。我们在开着加速下载的时候，统计了 PPE 对 WAN 进来的包是怎么处理的。没有这些修复时，每个包都作为没有路由的包送到 CPU。加上修复后，86 % 的包由 PPE 自己完成路由和地址转换。大约 2 % 仍然送到 CPU，这些是新连接的头几个包。剩下的 12 % 是 PPE 因为别的原因交给 CPU 的，具体原因我们还没弄清楚。

![开启加速时下载流量的包去了哪里](img/ppe-packet-path-zh.svg)

在 网络, 硬件加速 里打开。Wi-Fi 客户端的包仍然要经过一次 CPU，因为 ath12k 没法把包直接交给射频。

## 部分主板上的以太网接收问题

1.3.0 之前，部分板子装完固件后以太网收不到数据。链路是通的，但 MAC 一帧都收不到，Wi-Fi 却正常。原因出在供电上。DTS 里的 l2 稳压器是从 Qualcomm 参考板照搬过来的，内核通过 RPM 对它发出的请求让 SoC 在连接 QCA8084 的 10G-QXGMII 通道上的接收器失灵了，而这条通道的所有寄存器和时钟都和原厂固件一模一样。这个问题是在 zerc00l 的板子上找到的，我们可以远程登录那台设备做测试。修复是补丁 005。排查经过见 [issue #1](https://github.com/timofey-maykov/be7000-openwrt/issues/1) 和 4PDA 上的讨论帖。

## 5 GHz 上的两个射频

在原厂固件上，QCN9274 5 GHz 模块可以作为两个独立的射频（5G-1 和 5G-2）工作。为此原厂固件会加载另一套固件，也就是 dual-MAC 固件，并配上不同的板级数据（board id 是 0x1008 而不是 0x02）。这套固件本来就在 firmware-2.bin 里，ath12k 也能加载，但它只根据 OTP 里的 board id 来选，而 BE7000 的 OTP 里没有这个值。

| 补丁（mac80211, ath12k） | 作用 |
|------|-----------|
| 308 | DTS 里的 board id 也可以选中 dual-MAC 固件 |
| 309 | 使用固定射频内存时，把固件要的每一段内存都交给它。dual-MAC 要六段，其中包括 MLO 全局内存，给少了它就不会回应 |
| 310 | ath12k 模块参数 board_id，覆盖 DTS 里的 board id，带上 0x1000 位时取消 DTS 对射频数量的限制 |

模式用 be7000-5g-split（on, off, status）切换，也可以在 网络, 无线 页面顶部的 5 GHz 模式区域切换。脚本会设置参数，在 PCI 总线上重新绑定模块，不用重启路由器，然后在 Wi-Fi 配置里加上第二个 5 GHz 射频，并复制第一个射频上的网络。选择保存在 /etc/config/be7000。启动时 S09 的 init 脚本会在 ath12k 加载之前准备好模式，模块一启动就处在这个模式下。dual-MAC 用的板级数据是原厂的（bdwlan.b1008），以 board.bin 的名字打包。

和原厂固件（set_5g_split）一样，双射频模式下脚本会翻转射频控制线。TLMM6 设为 1，TLMM7 设为 0，单射频时反过来。DTS 用 pinctrl 状态而不是 gpio-hog 来设置这两根线，否则运行中没法改（tree 007）。原厂固件对双射频有单独的校准数据，在 ART 偏移 0x33000，单射频在 0x65000。脚本会把对应的那一份放进 ath12k 读取的文件里。

双射频时，iwinfo 只给每个射频列出它自己的信道（tree 008）。以前 LuCI 会把上半段射频的信道也提供给下半段射频，结果 AP 起不来。

## 5 GHz 固件崩溃

QCN9274 固件崩溃时，ath12k 会重启固件并重新建立数据通路。如果这时 hostapd 正在删除带有已连接客户端的 MLO 接口，或者 LuCI 正在读取信道统计，内核就会崩溃，路由器随之重启。

| 补丁（mac80211, ath12k） | 作用 |
|------|-----------|
| 312 | 固件恢复期间不再在读取者使用时释放 peer 地址表，表不存在时查找直接返回空，而不是读取零地址 |
| 313 | 只有在 CE 和 DP 环重新建立之后才清除 CRASH_FLUSH 标志，否则恢复期间发出的 WMI 命令会写进指向已释放内存的环 |
| 314 | 对按地址查找的站点表做同样处理，并且恢复失败后 WMI 命令和数据会被直接拒绝，不再写进拆了一半的环 |
| 315 | 删除 MLO 站点时跳过固件崩溃后已经没有 vdev 的链路，以前内核会在这种链路上读取零地址 |
